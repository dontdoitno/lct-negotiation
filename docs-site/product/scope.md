# Границы MVP

Страница отвечает на один вопрос: что в прототипе работает, а что решено не делать в этой итерации. Всё перечисленное проверено по коду, а не по планам.

## Реализовано

### Контент и сценарии

Шесть готовых сценариев в базе, по три типа личности на каждую из двух тем. Сценарий это одна запись, в которой ситуация и собеседник лежат вместе. Новые создаются в админке и появляются в каталоге сразу после публикации.

| Сценарий | Персонажи | Ходов | Слоёв интересов |
| --- | --- | --- | --- |
| `s1-overload`, «Перегрузка сотрудника», инициатор сотрудник | рациональный, тревожный, агрессивный | 14 | 3 у агрессивного и рационального, 4 у тревожного |
| `s3-performance-drop`, «Падение результатов», инициатор руководитель | рациональный, тревожный, агрессивный | 14 | 4 на персонажа |

Файлы в `content/` остались исходным материалом для сидов. Приложение читает сценарии только из базы.

Каждый персонаж описан полностью: матрица реакций на 19 действий, список адаптивных и неадаптивных для него действий, слои скрытых интересов с порогами доверия, по шесть заготовленных реплик на каждый из трёх уровней сопротивления, стартовое состояние метрик, реплика на входе и реплика на выходе из разговора.

### Движок и оценка

- Детерминированный движок состояния, `lib/engine/state.ts`, без обращений к модели.
- Условия финала, `lib/engine/endings.ts`: победа, срыв разговора, исчерпание ходов.
- Скрытый провал: договорённости есть, доверия нет. Правило считается от состояния и работает на всех шести уровнях.
- Подсчёт исхода по четырём показателям и звёзд за уровень, `lib/engine/scoring.ts`.
- 55 юнит-тестов: детерминизм, три ключевые асимметрии между типами личности, обрыв разговора на угрозе увольнением, финал по максимальному сопротивлению, сборка системного промта и перевод сценария в типы движка.

### Ход разговора

- Анализатор реплики, `lib/llm/analyzer.ts`. По умолчанию работает эвристика на ключевых словах, она бесплатная и мгновенная. Через `ANALYZER_LLM=true` классификацию можно отдать модели, ответ проверяется схемой Zod, при невалидном ответе происходит возврат к эвристике.
- Актёр, `lib/llm/actor.ts`. Стриминг реплики, две попытки, пост-фильтр на длину и на выход из роли, затем возврат к заготовленной реплике персонажа.
- Передача хода по SSE пятью событиями, от распознанных действий до готовой реплики.
- Голосовой ввод через Web Speech API на русском, `lib/call/useSpeechInput.ts`.

### Контур администратора

Список сценариев с фильтрами, сортировкой и полным CRUD без перезагрузки страницы. Конструктор на восемь секций с якорной навигацией, автосохранением и проверкой перед публикацией. Генерация черновика по шести полям через языковую модель, с запасным вариантом из пресета. Тест-прогон поверх готового экрана звонка с панелью отладки. Аналитика по прохождениям.

Роли две, `user` и `admin`. Раздел закрыт на уровне макета и на уровне каждого роута API. Подробности в разделе [Админка](../admin/overview.md).

### Пользовательский контур

Полный путь: лендинг, опрос из трёх вопросов, экран регистрации, правила, каталог разговоров, брифинг, звонок, экран финала, разбор. Отдельно обучение на шести шагах с практикой по таксономии действий, `/learn`.

**Каталог.** Слева колонка сфер, её можно свернуть. Число сценариев заранее неизвестно, поэтому вместо фиксированной сетки разговоры сгруппированы по темам. В ленте темы показываются три карточки сразу, остальные листаются вбок колесом или стрелками. На карточке стоит номер созвона, имя собеседника и чип сложности. Характер собеседника на карточке не написан и фильтра по нему нет: определить его по поведению это часть задачи.

**Видео-аватар собеседника.** В окне звонка вместо круга с буквой крутится короткий немой ролик. Аватаров три, администратор выбирает один из них в конструкторе, поле необязательное. Ролики лежат в `public/avatars` и весят около двухсот килобайт на все три, каждый идёт в двух форматах, webm и mp4, плюс первый кадр в webp как постер.

Идентификаторы файлов безличные, `avatar-1` и далее. Адрес виден в панели разработчика браузера, и назови мы файлы по характеру, тип личности читался бы прямо оттуда. По той же причине аватар не привязан к тону: одно лицо достаётся разным характерам.

**Экран звонка.** Занимает ровно высоту окна и сам не прокручивается. Прокрутка живёт внутри колонок, у описания сценария своя, у транскрипта своя, у панели метрик своя. Сделано ради одного: поле ввода не должно уезжать под нижний край по мере того, как растёт транскрипт.

**Разбор.** Исход по четырём показателям, метрики до и после, таймлайн с отметками перелома, слои интересов, разбор сработавшего и провального, переписанная реплика и привязка к ответу из входного опроса. Занимает всю ширину окна.

**Цветовые обозначения.** Чип сложности на карточке и шкала метрики в звонке используют один набор из трёх приглушённых цветов: зелёный в вашу пользу, янтарный посередине, красный против вас. Общий источник лежит в `lib/flow/severity.ts`. Значение при этом всегда написано словом или числом рядом, так что различать состояние по одному цвету не приходится.

### Провайдеры моделей

Yandex Cloud Foundation Models через нативный эндпоинт, Yandex Cloud через OpenAI-совместимый `/v1/responses` для сторонних моделей, OpenRouter, офлайн-режим без сети. Выбор автоматический по наличию ключей, принудительный через `LLM_PROVIDER`.

## Реализовано частично

Здесь лежит рабочая логика, до которой не доведён интерфейс. Об этом стоит знать заранее, потому что по экранам этого не видно.

**Ветвление сессии с точки слома.** `POST /api/session/:id/replay` создаёт форк сессии: копирует ходы до указанного номера, восстанавливает состояние на этот момент, связывает форк с родителем через `parentId` и `branchTurn`. Схема БД и API готовы и работают. Кнопки, которая это вызывает, в интерфейсе нет, повторное прохождение сейчас начинается с нуля.

**Фиксация договорённостей.** `POST /api/session/:id/commitments` принимает пункты в формате «что, кто, к какому сроку, как проверяем» и возвращает реакцию персонажа: принял, просит переделать пункт, отказался. Модальное окно `components/call/CommitmentsModal.tsx` написано и обращается к этому API. В экран звонка оно не подключено.

**Профиль паттернов игрока.** Движок в `lib/engine/patterns.ts` есть, экрана профиля нет.

**Регистрация.** Вход работает, аккаунты создаются сидами. Экран `/signup` собран и валидирует ввод, но новых пользователей не заводит. Гость по-прежнему опознаётся анонимной cookie `uid`, которую ставит `proxy.ts`, и его прогресс сохраняется по ней.

## Осознанно вынесено за скобки

**Генерация матрицы реакций моделью.** Матрицу пишет пресет тона, а не языковая модель. Это осознанный отказ ради воспроизводимости исхода: матрица и есть то, что делает результат разговора предсказуемым.

**Озвучка реплик сотрудника.** Распознавание речи есть, синтеза нет. Поле `voice` у персонажей заполнено под будущий TTS.

**Сценарий «Сложная задача»** из исходной спецификации. В контенте отсутствует, отсюда пропуск в нумерации между `s1` и `s3`.

**Экран сравнения веток и достижения.** Не начаты.

## Экспериментальный модуль рядом с основным

`lib/judge/*` это второй способ оценивать ход: дельты метрик каждый ход назначает языковая модель по рубрике гарвардского метода, а не заготовленная матрица психолога. Модуль живёт в отдельных таблицах `JudgeSession` и `JudgeTurn`, на отдельных путях `/api/judge/*`, и основной движок не трогает.

Это ветка исследования, а не основной путь продукта. Своего интерфейса у неё нет, вызывается из тестов и напрямую по API. Подробности в [LLM-судья](../architecture/judge.md).
