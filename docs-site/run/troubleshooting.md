# Если что-то не работает

## Сборка падает на нативном бинарнике

```
Cannot find module '../lightningcss.darwin-arm64.node'
```

Так же выглядят ошибки про `@tailwindcss/oxide`, `@next/swc` и `@rolldown/binding`.

Это несовпадение архитектуры, а не ошибка в коде. У npm есть [известный баг с опциональными зависимостями](https://github.com/npm/cli/issues/4828): при установке он оставляет бинарники только под ту архитектуру, в которой запущен сам, и выбрасывает остальные. Если `npm install` прошёл под Rosetta, то есть в x64, а `npm run dev` запускается нативно в arm64, сборка CSS ломается. Обратное сочетание ломается так же.

Посмотреть, что стоит:

```bash
ls node_modules | grep darwin
arch            # архитектура текущего терминала
node -p process.arch
```

Лечение: переустановить зависимости из обычного терминала, не из-под Rosetta.

```bash
rm -rf node_modules package-lock.json
npm install
```

## `npm run build` падает на `Can't resolve '@vercel/turbopack-next/internal/font/google/font'`

Ошибка повторяется десятками строк и выглядит как проблема со шрифтами, но дело не в них. Так проявляются несовместимые артефакты в папке `.next`: если в этом каталоге сначала работал `next dev`, а потом запускается `next build`, Turbopack спотыкается о результаты предыдущего режима.

```bash
rm -rf .next
npm run build
```

Проверено: после очистки сборка проходит. Архитектура тут ни при чём, ошибка одинаково воспроизводится и в arm64, и под Rosetta.

## Prisma не находит движок под вашу платформу

```
Query engine for current platform "darwin-arm64" could not be found
```

Клиент Prisma генерируется под платформу и в репозиторий не попадает.

```bash
npx prisma generate
```

В `prisma/schema.prisma` в `binaryTargets` перечислены `native`, `darwin`, `darwin-arm64` и `rhel-openssl-3.0.x`. Первые три покрывают macOS обеих архитектур, последний нужен рантайму функций на Vercel.

## Порт 3000 занят

```bash
npm run dev -- --port 3010
```

Посмотреть, кто занял порт: `lsof -nP -iTCP:3000 -sTCP:LISTEN`.

## Метрики не двигаются после реплики

Скорее всего анализатор распознал реплику как `small_talk`, а у этого действия нет дельт ни у одного персонажа.

В офлайн-режиме реплики разбирает эвристика на ключевых словах, и она узнаёт конкретные формулировки, а не смысл. «Вижу, что тебе тяжело» распознаётся как признание эмоции, «мне кажется, у тебя непростая ситуация» скорее нет. Полный список правил в `RULES` в `lib/llm/analyzer.ts`, а список действий с примерами в разделе [Метрики и действия](../reference/metrics.md).

Проверить, что именно распознано, можно по ответу SSE: событие `analysis` содержит коды действий, дельты и обоснование. Это же обоснование потом видно в таймлайне разбора.

Если нужен разбор по смыслу, а не по ключевым словам, поставьте `ANALYZER_LLM=true` при настроенном провайдере. Это удваивает расход на ход.

## Собеседник отвечает долго

Задержка идёт от модели. Две частые причины.

Модель размышляет перед ответом. DeepSeek, Qwen и подобные тратят на скрытое рассуждение выходные токены, и это добавляет секунды. Для реплики персонажа такая модель избыточна, `yandexgpt-lite` отвечает быстрее и дешевле.

Ответ не стримится. Режим `responses` у Yandex Cloud в нашем провайдере не стримит: схема событий этого эндпоинта не подтверждена, поэтому вместо догадок вызывается обычный `complete`, и текст приходит целиком. В режиме `native` стриминг работает.

## Yandex Cloud отвечает 404

Если в адресе фигурирует `completionStream`, то такого маршрута не существует. Потоковая генерация у Foundation Models включается полем `stream` в теле запроса на том же `/foundationModels/v1/completion`. В коде это уже так.

## Yandex Cloud отвечает 400 про каталог

Проверьте `YANDEX_FOLDER_ID`. Полезная деталь: в тексте ошибки Yandex Cloud обычно сам называет правильный идентификатор каталога, к которому привязан ключ.

## Модель вернула пустой текст

В режиме `responses` это означает, что бюджет выходных токенов кончился на скрытом рассуждении, и ответ пришёл со статусом `incomplete`. Провайдер поднимает `max_output_tokens` минимум до 1200, чтобы этого не происходило. Если всё равно случается, увеличьте потолок в `YANDEX_REASONING_TOKEN_FLOOR` в `lib/llm/provider.ts` или возьмите модель без скрытого рассуждения.

Отдельно: пустой ответ не ломает ход. Актёр делает две попытки, а затем берёт заготовленную реплику персонажа, и метрики при этом считаются как обычно.

## Реплики собеседника повторяются

Так выглядит офлайн-режим при коротком разговоре. Реплик по шесть на каждый из трёх уровней сопротивления, выбор зависит от номера хода и текущих метрик, а повтор предыдущей реплики отдельно исключается. Внутри одного уровня сопротивления вариантов всё равно шесть.

Чтобы реплики генерировались моделью, настройте ключи и снимите `MOCK_MODE="true"`.

## Разговор закончился раньше, чем ожидалось

Четыре штатных причины, все считаются движком:

- Сопротивление держалось на 90 и выше три хода подряд, сотрудник вышел из разговора.
- Прозвучала угроза увольнением на сопротивлении от 85: разговор обрывается сразу.
- Сделано 14 ходов.
- Выполнены все условия победы: сопротивление ниже 34, договорённости от 70, интересы от 70.

Третий случай легко получить быстрее, чем кажется. Реплика, в которой одновременно есть опора на данные, предложение варианта и фиксация со сроком, даёт большие дельты сразу по нескольким метрикам.

## База данных пустая или разговоры исчезли

Проверьте строку подключения и состояние миграций:

```bash
grep DATABASE_URL .env
npx prisma migrate status
```

Если таблиц нет, примените миграцию: `npx prisma migrate deploy`. Если `prisma` жалуется на `DATABASE_URL_UNPOOLED`, значит в `.env` нет второй строки подключения: миграции ходят в базу напрямую, мимо пула.

Посмотреть содержимое можно через `npx prisma studio`.
