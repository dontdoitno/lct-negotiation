# Модуль оценки ответов через LLM-судью (экспериментальный)

Параллельный режим оценки хода рядом с основным детерминированным движком
(`lib/engine/*`, задействован в `/api/session/*`). Здесь дельты метрик каждый
ход решает LLM по рубрике гарвардского метода, а не заранее просчитанная
матрица реакций психолога. Живёт в собственных таблицах БД и по собственным
API-путям — ничего в основном движке не меняет и не трогает.

## Архитектура

```
POST /api/judge/session               -> создать сессию
POST /api/judge/session/{id}/turn     -> один ход
GET  /api/judge/session/{id}/report   -> итоговый разбор

Ход:
  1. Предфильтр (lib/judge/prefilter.ts)  — чистые правила, БЕЗ LLM.
     Пусто/<3 слов, оффтоп-мусор, оскорбление, prompt injection —
     возвращает заготовленный ответ и нулевые (или фиксированные для
     оскорбления) дельты, судья и актёр не вызываются вообще.
  2. Judge (lib/judge/judge.ts)   — LLM, temperature 0.1, строго JSON,
     один ретрай на невалидный JSON, при повторной неудаче — деградация
     (все дельты 0, degraded: true).
  3. applyDeltas (lib/judge/applyDeltas.ts) — чистая функция: raw -2..2
     от судьи -> умножение на шаг -> клампинг ±10 за ход -> клампинг
     метрики в 0..100. Единственное место, где meняются абсолютные числа.
  4. Actor (lib/judge/actor.ts)   — LLM, temperature 0.7, реплика
     сотрудника с учётом уже применённых дельт.
  5. Персист хода в JudgeTurn, обновление JudgeSession.metrics.
```

## Метрики

Те же шесть метрик, что и в основном движке, под другими именами (см.
`lib/judge/types.ts::METRIC_TO_ENGINE_CODE` для маппинга):

| Имя в этом модуле | Код в основном движке |
|---|---|
| adaptation | A |
| trust | T |
| resistance (инвертирована — рост = хуже) | R |
| interests | I |
| solutions | S |
| commitment | C |

**Стартовые значения — персональные, не унифицированные.** Модуль переиспользует
`persona.initialState` из уже существующих `content/personas/*.json`
(рациональный/тревожный/агрессивный стартуют с разных R/T, как в
`docs/psyco_specs.md`), а не одно и то же 50/50/50/50/50/50 для всех —
это была явная договорённость при постановке задачи.

## Промпты

Все текстовые промпты — в `prompts/`, не в коде:

- `prompts/rubric.md` — определение метрик и техник + **места под 3-5
  якорных примеров «реплика → балл» на каждую метрику, помеченные
  `<!-- TODO(психолог) -->`**. Их нужно заполнить вручную.
- `prompts/judge.md` — шаблон промпта судьи.
- `prompts/actor_rational.md`, `actor_anxious.md`, `actor_aggressive.md` —
  по одному на тип личности, переиспользуются для обоих сценариев (контекст
  сценария подставляется как переменная, а не зашит в текст).

## Переменные окружения

См. блок в `.env.example`. Коротко:

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `JUDGE_LLM_CLIENT` | автоопределение | `mock` \| `yandex`. Пусто = yandex, если заданы `YANDEX_API_KEY`+`YANDEX_FOLDER_ID`, иначе mock. |
| `JUDGE_STEP` | 5 | множитель для дельты судьи (-2..2 -> ±10) |
| `JUDGE_MAX_DELTA_PER_TURN` | 10 | жёсткий потолок изменения одной метрики за ход |
| `JUDGE_TURN_LIMIT` | 12 | лимит ходов |
| `JUDGE_COMMITMENT_SUCCESS` | 80 | commitment ≥ это -> успех |
| `JUDGE_TRUST_FAIL` | 15 | trust ≤ это -> провал |
| `JUDGE_LLM_TIMEOUT_MS` | 20000 | таймаут на вызов LLM |

Реальные вызовы используют уже настроенные `YANDEX_API_KEY` /
`YANDEX_FOLDER_ID` / `YANDEX_MODEL` — отдельных ключей заводить не нужно.

## Демо-сессия на MockClient (без сети, без ключей)

```bash
export JUDGE_LLM_CLIENT=mock   # или просто не задавать реальные Yandex-ключи

# 1. создать сессию
curl -s -X POST http://localhost:3000/api/judge/session \
  -H "Content-Type: application/json" \
  -d '{"scenario_id":"s1-overload","persona":"aggressive"}'
# -> {"session_id": "...", "metrics": {...}, "reply": "Я больше не могу так работать!..."}

# 2. один ход
curl -s -X POST http://localhost:3000/api/judge/session/<session_id>/turn \
  -H "Content-Type: application/json" \
  -d '{"text":"Я вижу, что тебе тяжело — давай разберёмся, что можно снять с тебя по фактам."}'
# -> {"reply":"...", "metrics":{...}, "deltas":{...}, "techniques_used":[...], "turn":1, "finished":false, "degraded":false}

# 3. отчёт
curl -s http://localhost:3000/api/judge/session/<session_id>/report
```

С `MockClient` судья всегда возвращает один и тот же валидный ответ (кроме
случаев с маркерами `__FORCE_INVALID_JSON__` / `__FORCE_ERROR__` в тексте
реплики — так тесты проверяют ретрай и деградацию без сети).

## Тесты

```bash
npm test -- judge
```

Покрыто (`tests/judge.test.ts`): предфильтр (пустое/короткое, оффтоп-мусор,
оскорбление с правильными дельтами, prompt injection), клампинг и границы
дельт/метрик (включая случай, когда шаг больше потолка за ход), парсинг
ответа судьи через `MockClient` (валидный JSON, битый JSON -> деградация,
обрыв транспорта -> деградация), условия завершения уровня.

## Известные ограничения / что доделать

- Рубрика (`prompts/rubric.md`) без якорных примеров — судья работает по
  одним только определениям метрик, пока психолог не впишет примеры.
- Сценарий 2 («Сложная задача») пока не имеет авторского контента персонажей
  (`content/personas/s2-*.json` не существуют) — `POST /api/session` с
  `scenario_id: "s2-hard-task"` вернёт понятную ошибку, а не тихо сломается.
- Не проверено, поддерживает ли Yandex Foundation Models принудительную
  JSON-схему на стороне провайдера — поэтому схема валидируется у нас через
  zod, а не через `response_format` в запросе; ретрай/деградация на этом и
  основаны, так что это не блокер, просто не «нативный» structured output.
